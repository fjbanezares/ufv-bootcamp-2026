Sistemas Operativos:la base necesaria

Antes de un DataFrame, una consulta SQL o un modelo de inteligencia artificial, hay una máquina que necesita orden. Esta es la historia del software que lo hace posible.

Nivel · iniciaciónSesión sugerida · 60–75 min3 laboratorios interactivosSin dependencias externas
Tu código expresa lo que quieres hacer. El sistema operativo organiza con qué recursos, cuándo y bajo qué permisos podrá hacerlo.
01 / La pregunta que lo cambia todo

¿Quién trabaja cuando ejecutas tu código?

Escribes python analisis.py. Parece que Python se pone a trabajar y el ordenador obedece. Pero alguien ha tenido que localizar el ejecutable, crear un proceso, preparar su memoria, darle tiempo de CPU y permitirle abrir tus datos. Si además consultas una base remota, alguien mantiene la comunicación por red. Ese trabajo invisible pertenece, en gran medida, al sistema operativo.

Un sistema operativo (SO) es el conjunto de software que administra los recursos de un equipo y ofrece servicios para ejecutar aplicaciones. Resuelve tres problemas: abstraer la complejidad del hardware, repartir recursos escasos y proteger a unos programas de otros.

Imagina un laboratorio compartido. La CPU es una estación de trabajo; la RAM, las mesas; el almacenamiento, el archivo; la red, el servicio de mensajería. El SO organiza el uso de todo ello. La analogía tiene un límite: no entiende tus objetivos de negocio; aplica mecanismos y políticas, aunque tu programa esté haciendo algo inútil.

«Si mi portátil tiene ocho núcleos, ¿cómo puede tener cientos de procesos abiertos?»

Porque estar en ejecución como programa no significa estar usando la CPU en este instante. Muchos procesos esperan. Los demás se turnan.

02 / Anatomía mínima

Del notebook al silicio

Conviene separar cuatro cosas: la aplicación resuelve tu problema; las bibliotecas y runtimes le ofrecen funciones; el kernel administra los recursos esenciales; el hardware ejecuta instrucciones y mueve datos.

El espacio de usuario es donde viven normalmente las aplicaciones; el espacio del kernel ejecuta código con privilegios elevados. Una llamada al sistema es una petición controlada para cruzar esa frontera. Una suma de Python no exige por sí sola una llamada al kernel; leer bytes de un archivo puede exigirla.

El kernel es el núcleo del SO, pero no es todo el sistema. Tampoco lo son el escritorio ni la terminal. Puedes administrar un servidor sin ventanas, y el servidor sigue teniendo sistema operativo.

03 / Seis responsabilidades

Lo que el SO hace por ti

01. Repartir la CPU

El planificador decide qué tarea ejecutable recibe tiempo de procesador. Busca equilibrar respuesta, rendimiento y prioridades.

02. Administrar la memoria

Ofrece espacios de direcciones, asigna páginas y protege memoria. Gestiona también cachés y, cuando está configurada, la swap.

03. Organizar almacenamiento

Da nombres y estructura a los datos mediante sistemas de archivos. Gestiona metadatos, permisos y acceso a dispositivos.

04. Hablar con dispositivos

Los controladores o drivers traducen operaciones generales a instrucciones específicas para discos, red, pantallas o GPU.

05. Comunicar procesos

Pipes, señales, memoria compartida y sockets permiten que los programas colaboren dentro de una máquina y entre máquinas.

06. Aplicar protección

Usuarios, grupos, permisos y otros controles delimitan qué puede hacer cada proceso. El aislamiento reduce daños; no elimina todos los riesgos.

Una aplicación de datos termina tocando las seis. Un fallo que parece «de Python» puede ser un límite de memoria; uno que parece «de SQL», una espera de disco; uno que parece «de la nube», un permiso incorrecto.

04 / El arte de turnarse

Un programa no es un proceso

Un programa es código guardado. Un proceso es una instancia en ejecución, con identificador (PID), memoria, credenciales y recursos abiertos. Puedes ejecutar el mismo programa varias veces y obtener procesos distintos.

Un hilo es una unidad de ejecución dentro de un proceso; los hilos de un mismo proceso comparten memoria y otros recursos. En Linux el planificador trabaja con tareas, incluidos los hilos. Compartir facilita colaborar, pero también crea carreras: dos hilos pueden modificar el mismo dato sin coordinarse. Los bloqueos ayudan; si se esperan circularmente, puede aparecer un deadlock.

Concurrencia significa que varias actividades progresan durante un mismo intervalo. Paralelismo significa que se ejecutan simultáneamente. Con un solo núcleo puedes tener concurrencia: el SO alterna tareas mediante cambios de contexto. Estos cambios también cuestan tiempo.

05 / El espacio donde ocurre el trabajo

RAM, memoria virtual y el DataFrame gigante

El almacenamiento conserva información; la RAM mantiene datos e instrucciones que se necesitan durante la ejecución. El procesador cuenta además con cachés más pequeñas y rápidas. Mover datos entre niveles cuesta: no todo el tiempo de un cálculo se gasta calculando.

La memoria virtual da a cada proceso una visión propia de sus direcciones. El hardware y el kernel traducen esas direcciones a páginas físicas y comprueban accesos. No es sinónimo de swap: también permite aislamiento, mapeo de archivos y compartir páginas de forma controlada.

La swap permite almacenar ciertas páginas fuera de la RAM, pero no convierte el disco en RAM rápida. Si el sistema pasa demasiado tiempo intercambiando páginas, el rendimiento se hunde. Si no puede satisfacer las necesidades de memoria, una asignación puede fallar o el mecanismo OOM puede terminar un proceso.

Modelo simplificado: memoria residente, sin swap y con 2 GiB fijos para el SO. El consumo real incluye muchas más categorías.

Un CSV de 4 GB no garantiza un DataFrame de 4 GB. El formato en memoria, los tipos, las cadenas y las copias temporales pueden aumentar el tamaño. Leer por bloques o evitar copias puede servir más que añadir hilos.

En Linux, poca memoria «libre» no siempre es un problema: el SO usa RAM para caché de archivos y puede recuperar parte de ella. Mira también available en free -h, los límites del contenedor y la evolución del consumo.

06 / Datos que entran, salen y permanecen

Un archivo es más que su nombre

Un sistema de archivos organiza contenido y metadatos: tamaño, propietario, permisos y marcas de tiempo. En Linux, un inode representa metadatos y referencias al contenido; los directorios relacionan nombres con inodes. Un descriptor de archivo es el identificador que usa un proceso para trabajar con un recurso abierto.

La ruta /datos/ventas.csv empieza en la raíz /; datos/ventas.csv es relativa al directorio actual. Montar un sistema de archivos significa hacerlo accesible en un punto de ese árbol. Una carpeta llamada /datos puede estar sobre un SSD local, un volumen virtual o almacenamiento remoto.

Rendimiento ≠ solo capacidad

La latencia mide cuánto tarda una operación; el caudal, cuánto se transfiere por unidad de tiempo. Miles de archivos pequeños pueden resultar más lentos que uno grande del mismo tamaño total.

Escribir ≠ persistir inmediatamente

Una escritura puede quedar primero en caché. La durabilidad necesita mecanismos adecuados de sincronización y soporte del almacenamiento. Una base de datos añade sus propias garantías.

La frase «todo es un archivo» resume una filosofía útil, pero no es literal. Linux ofrece interfaces similares para muchos recursos: archivos, dispositivos, pipes y sockets. /proc expone información de procesos y del kernel; no es una carpeta de documentos normales en disco.

La red también pasa por el SO

Al conectar con PostgreSQL, el nombre del servidor se resuelve a una dirección mediante mecanismos como DNS; un socket permite comunicar los procesos; el kernel gestiona la pila de red. Una conexión TCP ofrece un flujo de bytes ordenado, pero no garantiza que una transacción de negocio se haya completado. Autenticación, TLS y SQL añaden otras capas.

08 / De la máquina exclusiva a la comunidad

Linux no apareció en el vacío

Los primeros ordenadores ejecutaban trabajos con mucha intervención manual. El procesamiento por lotes automatizó secuencias; el tiempo compartido permitió a varios usuarios interactuar con una máquina. La necesidad era la misma que hoy: aprovechar equipos caros sin que un trabajo monopolizara todo.

1969 · Unix

En Bell Labs comienza Unix, asociado a Ken Thompson y Dennis Ritchie. Su posterior desarrollo en C favorece la portabilidad. Herramientas combinables y una interfaz coherente dejan una huella profunda.

1983–1984 · GNU

Richard Stallman anuncia GNU en 1983; el trabajo comienza en 1984. El proyecto construye herramientas para un sistema libre de tipo Unix, entre ellas compiladores, utilidades y bibliotecas. [1]

1987 · MINIX

Andrew S. Tanenbaum presenta un sistema de tipo Unix orientado a la enseñanza. Su diseño permite estudiar ideas de sistemas operativos y forma parte del contexto en el que surge Linux.

1991 · Linux 0.01

Linus Torvalds desarrolla un kernel para PC con procesador 386. La primera versión pública es experimental: no es un escritorio completo ni una distribución lista para todos. [2]

1992 · GPL

Linux 0.12 adopta la GPL. El cambio favorece un modelo de colaboración y redistribución con obligaciones de licencia; la primera versión no tenía todavía esa licencia. [4]

1993–1994 · Distribuciones y versión 1.0

Slackware y Debian arrancan en 1993; Linux 1.0 llega en 1994. Las distribuciones integran piezas y hacen más manejable instalar, actualizar y mantener un sistema.

1996 · Linux 2.0

El soporte de multiprocesamiento simétrico es un hito para aprovechar varios procesadores. El proyecto sigue ampliando hardware y usos. [4]

Después · De los servidores a la nube

La evolución en red, virtualización, aislamiento y control de recursos abre nuevas posibilidades. Linux se desarrolla mediante una comunidad que incluye mantenedores, particulares y empresas.

La distinción importa: Linux es el kernel; una distribución es un sistema integrado alrededor de él. GNU aportó piezas fundamentales de muchas distribuciones, de ahí el nombre GNU/Linux. No todos los sistemas con kernel Linux usan el mismo entorno de usuario: Android es un ejemplo claro.

09 / Arqueología del código

Las primeras piezas de Linux

El árbol de Linux 0.01 permite reconocer responsabilidades que siguen siendo esenciales. Estas eran partes del código fuente, no módulos modernos que se cargaban a voluntad. [3]

DirectorioResponsabilidad inicial, a grandes rasgos
boot/Código de arranque y preparación inicial de la máquina.
init/Inicialización del kernel y puesta en marcha del sistema.
kernel/Planificación, procesos, llamadas al sistema y controladores tempranos.
mm/Gestión de memoria y fallos de página.
fs/Operaciones sobre archivos, inodes y buffers.
include/, lib/, tools/Cabeceras, rutinas auxiliares y herramientas de construcción.

Sus notas describen soporte limitado de hardware, un formato de archivos compatible con MINIX y dependencia de ese entorno para preparar el sistema. El kernel se escribía principalmente en C, con ensamblador para partes cercanas a la máquina. Todavía no era el Linux de red y hardware diverso que conocemos. [2]

¿Y los módulos cargables?

Llegaron después. Un módulo cargable incorpora código al kernel en funcionamiento, por ejemplo un controlador o un sistema de archivos, sin reconstruir todo el núcleo. lsmod muestra los módulos cargados; no muestra los componentes compilados directamente dentro del kernel. [5]

Linux es un kernel monolítico con capacidad modular. Sus subsistemas principales comparten un espacio privilegiado. Cargar una pieza separadamente no la convierte en un proceso aislado: un error en ella puede afectar al sistema completo.

Un microkernel mantiene menos funciones dentro del núcleo y desplaza otras a servicios separados, con comunicación entre ellos. Es una decisión arquitectónica con ventajas y costes; «micro» no significa automáticamente mejor, ni «monolítico» significa desorganizado.

10 / El sistema que encontrarás trabajando

Del botón de encendido al servicio de datos

En un arranque típico de un PC moderno, el firmware inicializa el equipo; un cargador carga el kernel; el kernel prepara dispositivos y memoria, y puede usar un entorno temporal initramfs antes de acceder al sistema raíz. Después, el proceso inicial de usuario, con PID 1, organiza servicios y sesiones. En muchas distribuciones ese papel lo desempeña systemd; no es obligatorio ni es el kernel.

Distribuciones: misma base, distintas decisiones

Debian y Ubuntu usan habitualmente paquetes DEB y APT; Fedora y RHEL, RPM y DNF; Arch, pacman. Cambian calendarios de actualización, valores por defecto y modelos de soporte. El gestor de paquetes resuelve dependencias del sistema; pip instala paquetes de Python. Confundir esos niveles suele producir entornos difíciles de reproducir.

LugarQué buscar allí
/homeDirectorios de usuarios en configuraciones habituales.
/etcConfiguración del sistema y de muchos servicios.
/varDatos variables: registros, cachés y estado de servicios.
/tmpArchivos temporales; no presupongas conservación.
/usrGran parte de programas y recursos instalados.
/dev, /proc, /sysInterfaces hacia dispositivos, procesos y estado del kernel.

Usuarios y permisos: tu proceso tiene identidad

En los permisos clásicos se distinguen propietario, grupo y otros. r, w y x significan lectura, escritura y ejecución en archivos; en directorios, x permite atravesarlos. chmod 640 ventas.csv concede lectura y escritura al propietario, solo lectura al grupo y ningún permiso a otros.

root dispone de amplios privilegios; sudo permite ejecutar comandos según una política de autorización. Dar 777 a todo no es arreglar permisos: es abrir accesos. Para un pipeline, define quién debe leer datos, escribir resultados y consultar secretos. ACL, capabilities y controles como SELinux amplían el modelo básico.

11 / Un lenguaje para componer tareas

La terminal no es el sistema operativo

La terminal permite interactuar mediante texto. El shell, como Bash, interpreta órdenes, expande variables y conecta programas. El kernel proporciona los mecanismos para ejecutarlos. Son piezas diferentes.

La idea Unix más fértil para los datos es la composición: programas pequeños que leen entradas, transforman y producen salidas. Los descriptores estándar son 0 (entrada), 1 (salida) y 2 (errores). Un pipe | conecta normalmente la salida estándar de un comando con la entrada del siguiente.

# Cuenta niveles de un registro sencillo, no un CSV general.
printf 'INFO inicio\nERROR disco\nINFO fin\n' | cut -d' ' -f1 | sort | uniq -c

> redirige la salida y puede sobrescribir un archivo; >> añade al final; 2> redirige errores. Las comillas importan para rutas con espacios. Usa un parser específico para CSV con comillas, separadores escapados o saltos de línea internos.

Una shell resulta poderosa porque las tareas se pueden guardar, repetir y auditar. Para automatizar, controla también códigos de salida, rutas, variables de entorno y errores. Un comando que funciona a mano puede fallar en un servicio porque cambia el usuario o el directorio de trabajo.

12 / Las mismas ideas, a otra escala

Docker y la nube no eliminan el SO

Máquina virtual

Presenta hardware virtual a un sistema invitado con su propio kernel. Un hipervisor administra la virtualización. Permite ejecutar varios sistemas sobre una misma infraestructura.

Contenedor Linux

Ejecuta procesos aislados que comparten el kernel del entorno anfitrión. Empaqueta aplicación y dependencias, pero no lleva normalmente un kernel propio.

Los namespaces separan vistas de recursos, como procesos o interfaces de red. Los cgroups permiten contabilizar y controlar recursos, como CPU y memoria. Son fundamentos de los contenedores Linux, junto a otros mecanismos de seguridad. [6] [7]

Un contenedor limitado a 2 GiB puede sufrir un OOM aunque el servidor tenga RAM disponible. En Docker Desktop, los contenedores Linux se ejecutan en un entorno Linux virtualizado; en Windows puede utilizarse WSL 2. Compartir kernel no significa compartir el kernel de macOS o Windows. [8]

Un entorno virtual de Python aísla dependencias de Python, no el sistema operativo. Kubernetes coordina cargas y contenedores entre nodos; no sustituye al kernel. Y serverless significa que el proveedor administra los servidores, no que hayan desaparecido.

Spark conecta las dos escalas. Spark distribuye tareas entre ejecutores; dentro de cada nodo, el SO sigue planificando hilos, administrando memoria y atendiendo disco y red. Un problema local puede convertirse en el retraso de todo el trabajo distribuido.

13 / Del síntoma a la hipótesis

«Va lento» no es un diagnóstico

Antes de cambiar parámetros, distingue qué recurso falta y mide durante el problema. CPU-bound significa limitado por cálculo; I/O-bound, por entrada/salida; memory-bound puede describir límites de capacidad o de acceso a memoria. Ninguna etiqueta sustituye las métricas.

SíntomaHipótesisPrimera comprobación
Un núcleo saturado; otros libresTrabajo secuencial o paralelismo insuficienteCPU por hilo y perfil de la aplicación; más núcleos no aceleran automáticamente código secuencial.
CPU baja y lectura lentaEspera de disco, red, bloqueo u otro servicioLatencia y caudal de E/S; registros; iostat si está instalado.
Proceso terminado inesperadamenteOOM, señal externa o fallo de aplicaciónLogs y límites de memoria. Un código 137 sugiere SIGKILL, pero no demuestra OOM por sí solo.
«Permission denied»Identidad o autorización incorrectasid, ls -l y permisos de directorios; después ACL u otros controles.
«No space left on device»Bloques, inodes o cuotas agotadosdf -h, df -i y cuotas aplicables.
Servicio remoto inaccesibleDNS, ruta, puerto, firewall o servidorResolver nombre, comprobar conexión y consultar logs. «No conecta» no equivale a «contraseña incorrecta».

Dos hábitos cambian la forma de trabajar: observar antes de reiniciar y modificar una variable cada vez. Conserva contexto suficiente para comparar: tamaño de entrada, versiones, recursos asignados y duración.

14 / Una primera exploración real

Diez minutos para mirar debajo

En una terminal Linux con Python 3 disponible, ejecuta estas órdenes como usuario normal. La práctica crea únicamente un directorio temporal y un archivo dentro de él; no necesita privilegios de administrador.

# 1. Identidad, ubicación y kernel
whoami
pwd
uname -r

# 2. Memoria y espacio del sistema de archivos actual
free -h
df -h .

# 3. Un directorio nuevo para el experimento
practica_so_dir=$(mktemp -d)
cd "$practica_so_dir" || exit 1
printf 'origen,filas\nweb,120\napp,80\n' > muestra.csv
ls -l muestra.csv
wc -l muestra.csv

# 4. Crea un proceso y obsérvalo mientras espera
python3 -c 'import os,time; print("PID:",os.getpid(),flush=True); time.sleep(30)' &
practica_so_pid=$!
ps -p "$practica_so_pid" -o pid,ppid,stat,comm
wait "$practica_so_pid"

Qué deberías observar: wc -l devuelve tres líneas, aunque haya solo dos registros de datos; el proceso de Python tiene un PID; durante sleep está normalmente en estado de espera, sin ocupar continuamente un núcleo. La salida puede variar según tu entorno.

Para discutir: ¿por qué leer un archivo por segunda vez puede ser más rápido?

Porque sus páginas pueden seguir en la caché de archivos del SO. La segunda lectura quizá necesite menos acceso al dispositivo. No demuestra que el disco haya mejorado ni que el algoritmo sea distinto.

Para discutir: ¿un contenedor con Ubuntu trae su propio kernel Ubuntu?

Normalmente no. La imagen aporta un entorno de usuario de Ubuntu; los procesos utilizan el kernel del anfitrión Linux, que puede estar dentro de una máquina virtual.

Para discutir: ¿añadir ocho hilos divide el tiempo entre ocho?

No necesariamente. Influyen el paralelismo real, las partes secuenciales, las esperas, la coordinación y el recurso que limita. En CPython también importa la configuración del intérprete y si las bibliotecas liberan el GIL.

Para discutir: ¿quién «entiende» una consulta SQL?

El motor de base de datos interpreta y ejecuta SQL. El SO le proporciona procesos, memoria, archivos y comunicación; no necesita comprender la consulta ni sus resultados.

15 / La idea que queda

La nube sigue teniendo suelo

La historia de los sistemas operativos es la historia de cómo compartir una máquina sin convertirla en un caos. Cada abstracción simplifica el trabajo: archivos en lugar de sectores, procesos en lugar de instrucciones dispersas, sockets en lugar de manipular directamente una tarjeta de red.

Linux añade otra lección: un núcleo pequeño y limitado puede crecer gracias a interfaces, herramientas compartidas y colaboración sostenida. Su valor para un profesional de datos no consiste en memorizar cientos de comandos, sino en reconocer qué está ocurriendo debajo de cada herramienta.

De «mi código falla» a «sé dónde mirar».

Ante cualquier carga de datos, hazte cinco preguntas:

  1. ¿Qué proceso está trabajando y con qué identidad?
  2. ¿Dónde están los datos y qué camino recorren?
  3. ¿Qué recurso limita: CPU, memoria, disco o red?
  4. ¿Qué permisos y límites se aplican?
  5. ¿Qué evidencia confirma mi hipótesis?

Entender el sistema operativo es aprender a formular mejores preguntas a la máquina.

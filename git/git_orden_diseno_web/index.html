Git: orden por diseño y colaboración distribuida.

ANTES DE LOS COMANDOS

Git tiene sentido cuando entiendes su diseño

1. Git es local primero

Tu repositorio local contiene la historia y puede crear commits, ramas, merges y diffs sin hablar con GitHub, GitLab o ningún servidor.

2. Un commit es una instantánea

No es “una lista de líneas cambiadas”. Conceptualmente es una foto del árbol completo del proyecto, enlazada a su padre.

3. Una rama es barata

Una branch es básicamente una referencia móvil a un commit. Crear una rama no duplica el proyecto.

4. Git mueve referencias

Buena parte de Git consiste en crear objetos inmutables y después mover nombres: main, feature-x, HEAD, tags y remotos.

Idea central: Git funciona muy bien porque separa tres preguntas: “¿qué tengo ahora?”, “¿qué quiero incluir en la próxima foto?” y “¿qué fotos ya forman parte de la historia?”.
01 · MODELO MENTAL

Las tres zonas: WD → Staging → Repository

El error más frecuente al aprender Git es imaginar que solo existen “mis archivos” y “GitHub”. Entre medias hay un área decisiva: el staging area, también llamada index.

A

Working Directory

Los archivos que ves y editas.

  • Pueden estar modificados.
  • Pueden ser nuevos y aún no rastreados.
  • Un cambio aquí todavía no forma parte del próximo commit.
git status
→ git add →
B

Staging Area / Index

La selección exacta de la próxima instantánea.

  • Permite preparar solo parte del trabajo.
  • Hace posible construir commits conceptualmente limpios.
  • No es una carpeta visible: es una estructura interna de Git.
git diff --staged
→ git commit →
C

Repository

La base de datos local de objetos e historia.

  • Commits ya registrados.
  • Ramas, tags y referencias.
  • Contenido bajo .git/.
git log

¿Por qué existe staging?

Porque “lo que he cambiado” y “lo que quiero convertir en un commit” no tienen por qué ser lo mismo. Has podido modificar cuatro archivos para investigar un bug, pero quizá el commit correcto solo deba incluir dos.

Dos diffs distintos

git diff
# Working Directory ↔ Staging

git diff --staged
# Staging ↔ último commit

Y una tercera comparación útil

git diff HEAD
# Working Directory + Staging
# contra el commit actual
02 · QUÉ GUARDA GIT

Git es una base de datos de objetos direccionados por contenido

La carpeta .git contiene la maquinaria. Git identifica objetos mediante hashes. Eso permite detectar contenido idéntico, referenciarlo y construir historia verificable.

blob

Contenido de archivo

Un blob representa bytes de un archivo. No “sabe” su nombre: el nombre vive en el tree.

tree

Directorio

Relaciona nombres con blobs y subtrees. Es la estructura jerárquica de la instantánea.

commit

Instantánea + contexto

Apunta a un tree, a uno o más padres, autor, fecha y mensaje.

tag

Nombre estable

Puede apuntar a un commit para marcar una versión como v2.4.0.

commit C3
tree T3 · parent C2
↓
tree T3
src/ · README.md
↙︎      ↘︎
blob
README
tree
src/
Una consecuencia profunda: los commits son esencialmente inmutables

Si cambias su contenido, su metadata o su padre, cambia su identidad. Por eso operaciones como rebase o commit --amend no “editan” commits antiguos en el sentido tradicional: generan commits nuevos.

03 · FLUJO BÁSICO

De carpeta normal a historia versionada

01

Inicializar

git init

Crea .git/. La carpeta pasa a ser un repositorio.

02

Inspeccionar

git status

Pregunta imprescindible: qué está modificado, staged o sin rastrear.

03

Seleccionar

git add app.js
git add .
git add -p

-p permite elegir fragmentos concretos.

04

Fotografiar

Crea un nuevo commit desde el index.

Estados típicos de un archivo

untracked→ git add →staged→ commit →tracked / clean→ editar →modified
ComandoQué hace realmenteError mental típico
git add archivoCopia la versión actual del archivo al index.Creer que “avisa a Git” una sola vez.

.gitignore no es una papelera

# Ejemplo
node_modules/
.env
dist/
*.log
.DS_Store

.gitignore evita que archivos no rastreados entren accidentalmente. Si un archivo ya está versionado, añadirlo al ignore no lo elimina de la historia ni deja de seguirlo automáticamente.

04 · RAMAS Y HEAD

Una rama es un nombre que apunta a un commit

Esta idea elimina mucha magia. La rama no es una “carpeta paralela”: es una referencia móvil. Cuando confirmas cambios, la rama activa avanza al nuevo commit.

A──B──C──D main
└────E──F feature/login

Crear y cambiar

git branch feature/login
git switch feature/login

# En una línea:
git switch -c feature/login

Ver ramas

git branch
git branch -vv
git branch --all

HEAD: “dónde estoy”

Normalmente HEAD apunta a la rama activa, y esa rama apunta al commit actual. Por tanto: HEAD → main → commit D.

¿Qué es “detached HEAD”?

Significa que HEAD apunta directamente a un commit, no a una rama. Puedes explorar y hasta crear commits, pero conviene crear una rama si quieres conservar cómodamente ese trabajo: 

git switch -c rescate-experimento
05 · MERGE

Merge: conservar dos líneas de historia y unirlas

Un merge pregunta: “¿cómo hago que esta rama incluya también el trabajo de aquella?”. Dependiendo de la topología, puede bastar con mover un puntero o requerir un commit de fusión.

Fast-forward

A — B — C — D

Si main no ha divergido, Git puede simplemente adelantar main hasta D.

git switch main
git merge feature

Three-way merge

A — B — C \ \ D — M

Si ambas ramas avanzaron, Git busca ancestro común y crea normalmente un commit de merge M.

git switch main
git merge feature

Merge no significa “copiar archivos”

Git compara historias y combina cambios relativos al ancestro común. Esta diferencia explica por qué puede fusionar automáticamente trabajo realizado en zonas distintas del mismo proyecto.

--no-ff fuerza un commit de merge incluso cuando el fast-forward sería posible. Puede ser útil si quieres que la existencia de una feature quede explícita en el grafo.
06 · REBASE

Rebase: reescribir la base de una serie de commits

Mientras merge une historias, rebase toma commits y los recrea encima de otra base. El resultado suele ser más lineal, pero los hashes cambian.

Antes

A — B — C   main
     \
      D — E feature

Después de git rebase main

A — B — C   main
         \
          D' — E' feature
git switch feature
git rebase main
Importante: rebase cambia historia. Es excelente con commits locales que controlas. Evita rebasar historia pública compartida si otros ya construyeron trabajo sobre esos commits.

Rebase interactivo: editar tu propia narrativa

git rebase -i HEAD~5
pick conservar reword cambiar mensaje edit detenerse y modificar squash combinar conservando mensajes fixup combinar descartando mensaje menor drop eliminar commit

Merge vs Rebase

MergeRebase
HistoriaPreserva divergencia real.La linealiza.
Hashes existentesNormalmente no cambian.Los commits rebasados se recrean.
Uso típicoIntegración de ramas.Actualizar una feature antes de integrarla.
RiesgoGrafo más ruidoso.Reescribir historia compartida.
07 · CONFLICTOS

Un conflicto no es un fallo: es una decisión que Git no puede tomar por ti

Si dos historias modifican de manera incompatible la misma zona, Git necesita contexto humano. Señala el punto y detiene la operación. 

<<<<<<< HEAD
precio = calcularPrecioVIP();
=======
precio = calcularPrecioPromocional();
>>>>>>> feature-promos
1

Leer

Identifica la intención de ambos cambios.

2

Resolver

Edita el archivo y elimina los marcadores.

3

Stagear

git add archivo
4

Continuar

git merge --continue
# o
git rebase --continue
Si quieres abandonar la operación: git merge --abort o git rebase --abort.
08 · DESHACER SIN DRAMA

“Deshacer” puede significar cuatro cosas distintas

Antes de usar un comando destructivo, pregunta qué quieres cambiar: ¿el Working Directory, el staging, el puntero de la rama o una historia ya publicada?

Quiero…ComandoIdea
Descartar cambios locales de un archivogit restore archivoRestaura desde el index.
Sacar algo del staginggit restore --staged archivoUnstage; conserva cambios en WD.
Corregir el último commitgit commit --amendRecrea el último commit.
Deshacer un commit publicadogit revert HASHCrea un commit inverso; no borra historia.
Mover la rama hacia atrás conservando staginggit reset --soft HEAD~1Mueve referencia; index intacto.
Mover rama y desstagear cambiosgit reset HEAD~1Modo mixed por defecto.
Volver atrás destruyendo cambios localesgit reset --hard HEAD~1Peligroso: altera WD e index.

El salvavidas: reflog

git reflog

reflog registra por dónde han pasado referencias locales como HEAD. Si moviste una rama por error, muchas veces el commit “perdido” sigue existiendo y puedes recuperarlo. 

git reflog
# ... aparece abc1234 HEAD@{3}

git switch -c rescate abc1234
Piensa dos veces antes de reset --hard. Git suele poder recuperar commits; los cambios locales nunca registrados pueden ser mucho más difíciles de rescatar.
09 · STASH

Stash: aparcar cambios sin convertirlos todavía en commit

Útil cuando necesitas cambiar de contexto rápidamente pero tu trabajo actual aún no merece un commit. El stash es una pila de estados temporales. 

git stash
git stash push -m "WIP validación"
git stash list
git stash apply stash@{0}
git stash pop
git stash drop stash@{0}
apply reaplica y conserva el stash. pop reaplica y, si todo va bien, lo elimina.

No conviertas el stash en un “trastero de meses”. Para trabajo importante y duradero, una rama y commits provisionales suelen ser más visibles y seguros.

10 · REPOSITORIOS REMOTOS

Git distribuido: remoto no significa “repositorio principal” por necesidad técnica

Un remoto es otro repositorio identificado por un nombre y una URL. Por convención, el primero suele llamarse origin.

Tu portátil

main feature origin/main
push → ← fetch

Servidor remoto

main feature

clone

git clone https://servidor/proyecto.git

Crea una copia local, configura origin y obtiene referencias remotas.

fetch: mirar sin integrar

git fetch origin

Descarga objetos y actualiza referencias como origin/main. No modifica automáticamente tu rama local main.

pull: descargar + integrar

git pull
# aproximadamente:
git fetch
git merge   # según configuración

También puede configurarse para rebase: 

git pull --rebase

push: publicar referencias y objetos

git push origin main

# Primera vez de una rama:
git push -u origin feature/login

-u establece la rama remota de seguimiento (upstream).

main

Tu rama local. Tú la puedes mover creando commits, merges, resets, etc.

origin/main

Tu última representación local conocida del estado de main en origin, normalmente actualizada por fetch.

¿Por qué un push puede ser rechazado?

Porque el remoto contiene commits que tu rama local no incluye. Git evita sobreescribirlos por accidente. Primero debes integrar esa historia o decidir explícitamente una estrategia de reescritura.

Si realmente necesitas reescribir una rama remota, git push --force-with-lease suele ser más prudente que --force, porque comprueba que el remoto no haya avanzado inesperadamente.
11 · COLABORACIÓN

Git separa integración técnica de política de equipo

Git sabe mover y combinar historia. El equipo decide cómo quiere organizar ese trabajo: ramas cortas, pull requests, revisiones, integración continua, tags, releases, etc.

Feature Branch

Una rama por cambio. Muy común con Pull/Merge Requests y revisión de código.

Trunk-Based

Ramas muy cortas o commits frecuentes sobre una rama principal protegida. Favorece integración continua.

GitFlow

Modelo con develop, features, releases y hotfixes. Más ceremonioso; útil en ciertos ciclos de release.

Fork Workflow

Cada contribuidor trabaja desde su fork y propone cambios al repositorio original.

Un flujo sano de feature

git switch main
git pull --ff-only

git switch -c feature/buscador

# trabajar
git add -p
git commit -m "Añade búsqueda por título"

git fetch origin
git rebase origin/main

git push -u origin feature/buscador
# abrir Pull Request / Merge Request

Commits pequeños pero con significado

  • Un commit debe representar una idea coherente.
  • Debe poder explicarse con una frase.
  • Idealmente compila y deja tests razonablemente sanos.
  • Separar refactor y cambio funcional facilita revisión y reversión.
  • “WIP, arreglos, cosas” dicen poco; el mensaje debe explicar intención.

Los Pull Requests no son parte del núcleo de Git

Son una capa de colaboración ofrecida por plataformas como GitHub, GitLab o Bitbucket. Git por sí mismo no necesita PRs para fusionar ramas.

12 · LEER LA HISTORIA

Saber consultar Git vale tanto como saber escribir en él

git log

Historia de commits.

git log --oneline

Vista compacta.

git log --graph --all

Topología de ramas.

git show HASH

Commit + cambios.

git diff A..B

Diferencias entre dos puntos.

git blame archivo

Commit asociado a cada línea actual.

git log --graph --decorate --oneline --all
Crea un alias para no escribirlo siempre: git config --global alias.lg "log --graph --decorate --oneline --all"
13 · HERRAMIENTAS AVANZADAS

Git tiene herramientas quirúrgicas para problemas concretos

cherry-pick

git cherry-pick abc1234

Aplica el cambio introducido por un commit concreto sobre la rama actual, creando un commit nuevo.

bisect

git bisect start
git bisect bad
git bisect good v2.0

Búsqueda binaria para encontrar qué commit introdujo un fallo.

tags

git tag -a v3.0.0 -m "Release 3.0"

Marcan puntos estables de historia. Muy usados para releases.

worktree

git worktree add ../hotfix hotfix

Permite tener varias ramas del mismo repo abiertas en directorios distintos.

sparse-checkout

git sparse-checkout init --cone

Útil en repos grandes cuando solo quieres materializar parte del árbol de trabajo.

hooks

.git/hooks/pre-commit

Scripts disparados por eventos. Pueden validar formato, tests o políticas antes de ciertas operaciones.

Submodules: repositorios dentro de repositorios

Un submodule registra una referencia a un commit de otro repositorio. Es potente pero introduce complejidad de sincronización. No es simplemente “una carpeta Git normal”.

Firma de commits y tags

Git permite asociar firmas criptográficas a commits y tags para mejorar garantías de autoría e integridad en flujos que lo requieren.

14 · BUENAS PRÁCTICAS

La calidad de un repositorio se nota en su historia

Haz

  • git status con frecuencia.
  • Revisa el staged diff antes del commit.
  • Haz commits conceptuales y pequeños.
  • Sincroniza antes de empezar trabajo conflictivo.
  • Usa ramas cortas para reducir divergencia.
  • Protege main en equipos.
  • Usa reflog antes de asumir que algo se perdió.

Evita

  • Commit de secretos, claves o .env.
  • git add . ciego en repos grandes.
  • push --force sobre ramas compartidas.
  • Rebase arbitrario de historia pública.
  • Commits gigantes con muchas ideas mezcladas.
  • Usar Git como almacén de binarios pesados sin estrategia.
  • Arreglar conflictos sin entender ambas intenciones.

Una estructura de mensaje útil

Añade caché a consultas de catálogo

Evita repetir consultas idénticas durante 30 segundos.
Reduce carga sin cambiar la API pública.

El título cuenta qué cambia; el cuerpo explica por qué, especialmente cuando la decisión no es obvia leyendo el diff.

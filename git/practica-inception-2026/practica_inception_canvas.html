Puesta a Punto del Entorno (IDE y Git Pull)

Cómo preparar tus herramientas de trabajo y sincronizar el repositorio sin romper nada.

Para realizar esta práctica utilizaremos **Antigravity IDE** (o Visual Studio Code) junto a la consola de comandos de Git (**Git Bash** en Windows, o la **Terminal** en macOS / Linux).

A. Si ya clonaste el repositorio en clase (Caso General)

Abre tu terminal dentro de la carpeta del repositorio y realiza estas dos comprobaciones obligatorias antes de tocar nada:

1. Verificar el Servidor Remoto con git remote -v

El comando git remote -v muestra con qué servidor central de GitHub está emparejado tu ordenador:

Terminal / Git Bash 
git remote -v

Debe responderte con la URL oficial de la clase:

Salida esperada
origin  https://github.com/fjbanezares/ufv-bootcamp-2026.git (fetch)
origin  https://github.com/fjbanezares/ufv-bootcamp-2026.git (push)

* origin es el alias por defecto que recibe el repositorio remoto en la nube.
* fetch es la ruta de donde descargas datos y push hacia donde los subes.

2. Traer la nueva práctica con git pull

git pull es una orden compuesta que hace dos cosas en un solo paso: 1. Fetch: Descarga todos los commits y carpetas nuevas que el profesor ha publicado en GitHub. 2. Merge: Las fusiona automáticamente dentro de tu copia local.

Terminal / Git Bash 
git checkout main
git pull origin main

Comprueba que ya puedes ver la carpeta de la práctica ejecutando:

Terminal / Git Bash 
ls -la git/practica-inception-2026/
🚨 ¿Te ha fallado el git pull? Aquí tienes la solución

Si al hacer git pull la terminal te escupe un error como: "Your local changes to the following files would be overwritten by merge" o te indica que tus ramas han divergido, es porque escribiste o modificaste archivos directamente en main.

Paso de diagnóstico: Ejecuta git status para ver qué tienes modificado.

  • Si solo son archivos tocados sin hacer commit: Restáuralos a su estado original con git restore . (o guárdalos en un cajón temporal con git stash).
  • Si hiciste un commit local en main: Puedes deshacerlo de forma limpia con git revert HEAD (o sincronizar tu main de golpe con el del profesor ejecutando git reset --hard origin/main).

Una vez limpio, repite git pull origin main y verás la práctica al instante.

B. Si eres nuevo o no tenías el repositorio clonado

1. Instala Git: Descarga Git para Windows (Git Bash) o instálalo en Mac mediante brew install git.
2. Instala Antigravity IDE: Descarga e inicia Antigravity IDE (o Visual Studio Code).
3. Configura tu identidad:

Configuración Global de Git 
git config --global user.name "Tu Nombre y Apellidos"
git config --global user.email "tu_email@alumnos.ufv.es"

4. Clona el repositorio oficial de la clase:

Clonar repositorio 
git clone https://github.com/fjbanezares/ufv-bootcamp-2026.git
cd ufv-bootcamp-2026

¿Qué es una Rama? Creando tu Workspace Aislado

Por qué nunca se programa en producción y cómo bifurcar tu propia línea temporal.

Imagina que estás escribiendo un libro entre 14 autores. Si todos intentaran escribir al mismo tiempo en el único folio que hay sobre la mesa, se tacharían unos a otros, se mancharían de tinta y el libro quedaría destruido.

En Git, una rama (branch) es una copia ligera e independiente de tu código. Es un puntero móvil de apenas 41 bytes que te permite construir una realidad paralela:

  • Puedes experimentar, equivocarte, borrar y probar sin miedo a romper el trabajo de los demás.
  • La rama principal (main) permanece siempre limpia, estable y funcionando al 100%.
  • Cuando tu trabajo esté terminado y validado por el profesor, tu rama se fusionará con main.

Crear tu rama de trabajo personal

Vamos a crear una rama con una nomenclatura profesional que incluya tu nombre y apellidos:

Crear y cambiar de rama 
# Sintaxis clásica:
git checkout -b feature/inception-tu-nombre-apellido

# O con la sintaxis moderna de Git:
git switch -c feature/inception-tu-nombre-apellido
Comprobación de Seguridad

Ejecuta git branch en tu terminal. Verás un asterisco verde al lado de tu rama:

Salida esperada
* feature/inception-tu-nombre-apellido
  main

¡Felicidades! Todo lo que hagas a partir de este instante ocurrirá dentro de tu burbuja segura.

Python LEGB y el Misterio de Inception

Entendiendo cómo Python busca y manipula variables a través de capas anidadas.

Antes de mirar el código, asegúrate de tener listo tu entorno de desarrollo en **Antigravity IDE**:

Activar la Extensión de Python en Antigravity IDE

1. En la barra lateral izquierda de Antigravity IDE, haz clic en el icono de Extensiones / Plugins (icono de bloques o cuadrados).
2. Escribe Python en el buscador.
3. Asegúrate de que la extensión oficial de Python esté instalada y habilitada para disfrutar de coloreado de sintaxis, autocompletado y depuración en vivo.

La Regla de Oro: El Ámbito LEGB

Cuando en Python utilizas una variable llamada x, el intérprete no la busca al azar. Sigue una jerarquía estricta de 4 niveles conocida como **LEGB**:

Ámbito Significado Equivalente en la película Inception
L - Local Variables creadas dentro de la función activa actual. Mueren cuando la función termina. El Limbo (el rincón más profundo del subconsciente).
E - Enclosing Variables de las funciones exteriores que envuelven a la función actual. Los Niveles de Sueño 1, 2 y 3 (París, Hotel, Fortaleza).
G - Global Variables definidas en la raíz del archivo/módulo (fuera de toda función). La Realidad (el avión Boeing 747 volando sobre el océano).
B - Built-in Nombres reservados del propio lenguaje Python (print, len, range). Las Leyes de la Física universales.

La Arquitectura del Código: scope_inception.py

Abre el archivo git/practica-inception-2026/scope_inception.py. Observarás cómo cada función anidada representa un nivel de sueño más profundo:

✈️ Nivel 0: REALIDAD (Mundo Exterior) GLOBAL
x = "Real World"
🌧️ Nivel 1: SUEÑO EN PARÍS (Yusuf / Lluvia) ENCLOSING 1
x = "Dream Level 1: Paris"
🏨 Nivel 2: SUEÑO EN EL HOTEL (Arthur / Gravedad Cero) ENCLOSING 2
x = "Dream Level 2: Hotel"
❄️ Nivel 3: FORTALEZA DE NIEVE (Eames / Nieve) ENCLOSING 3
x = "Dream Level 3: Snow Fortress"
🌀 Nivel 4: EL LIMBO (El Abismo Profundo) LOCAL
global x | nonlocal_real_world_x = x

El Efecto Mágico: global vs nonlocal

¿Qué ocurre cuando estamos en lo más hondo del Limbo?

  • La palabra clave global x: Salta mágicamente todos los sueños intermedios (la nieve, el hotel y París) y modifica directamente el mundo real en el avión (x = "Real World, but altered").
  • La palabra clave nonlocal: Permite tomar una variable de la función envolvente inmediata (el Nivel 3 de la nieve) y modificarla sin alterar el mundo real exterior.

Pruébalo ejecutándolo directamente en tu terminal:

Ejecutar script en Terminal 
python3 git/practica-inception-2026/scope_inception.py
Salida en pantalla
In the Real World, starting to dream...
In Dream Level 1: Paris, starting to go deeper...
In Dream Level 2: Hotel, starting to go deeper...
In Dream Level 3: Snow Fortress, starting to go deeper...
In Limbo, reality is: Real World
In Limbo, after altering reality, the Dream Level 3 is: Real World, but altered
Back in Dream Level 3: Snow Fortress, after Limbo.
Back in Dream Level 2: Hotel, after Dream Level 3.
Back in Dream Level 1: Paris, after Dream Level 2.
Back in the Real World, but altered.

¡Fíjate en la última línea! Cuando despertamos de todos los niveles, la realidad ya no es `"Real World"`, sino `"Real World, but altered"`. La alteramos desde el fondo del subconsciente.

La Tarea: Tu Análisis Personal de Scopes

Cómo realizar tu aportación respetando el código para evitar conflictos al fusionar 14 ramas.

En la carpeta git/practica-inception-2026/soluciones/ tienes a tu disposición 6 variantes avanzadas desarrolladas como referencia técnica (orientadas a objetos con tótems, generadores con yield para "The Kick", with context managers con Yusuf, etc.).

¡Atención! La regla de oro para la fusión grupal

En este bootcamp somos 14 alumnos. Si cada alumno reescribe y destruye el código de forma completamente diferente, cuando el profesor intente fusionar las 14 ramas en main, se producirá un infierno de conflictos inasumibles.

Por lo tanto, la mejora obligatoria consiste en documentar y enriquecer el archivo con tu análisis firmado.

Instrucciones exactas para tu cambio:

  1. Abre el archivo git/practica-inception-2026/scope_inception.py en tu editor.
  2. En la parte superior o justo antes de la función limbo(), añade un bloque de comentarios con tu nombre y apellidos completo delante:
    Ejemplo de comentario a insertar
    # ==============================================================================
# ALUMNO: [TU NOMBRE Y APELLIDOS AQUÍ]
# REFLEXIÓN DE SCOPES:
# El uso de 'global' aquí permite alterar la variable 'x' de la realidad
# desde el Limbo, saltándose los niveles de sueño 1, 2 y 3.
# Por su parte, 'nonlocal' permite comunicarse con el nivel inmediatamente
# superior sin contaminar la realidad global exterior.
# En producción, abusar de 'global' genera efectos secundarios peligrosos
# porque una función oculta puede alterar el estado de todo el sistema.
# ==============================================================================
  3. Guarda el archivo y vuelve a ejecutarlo (python3 git/practica-inception-2026/scope_inception.py) para verificar que no has roto la sintaxis y sigue imprimiendo los sueños perfectamente.

Ciclo Local de Git y tu Mejor Amigo: git log

Del Staging Area al árbol genealógico de commits con visualización gráfica.

Ya has modificado el archivo en tu disco duro. Ahora vamos a registrar ese cambio en el historial inmutable de Git en dos pasos:

1. git add: La Zona de Preparación (Staging Area)

Guardar un archivo en el editor no significa que Git lo haya fotografiado. Con git add le dices a Git: "Pon este archivo en la bandeja de salida para el próximo envío".

Terminal / Git Bash 
git status
git add git/practica-inception-2026/scope_inception.py
2. git commit: La Foto Inmutable

Un commit es una instantánea permanente en la historia del proyecto. Requiere un mensaje claro que explique el qué y el por qué:

Terminal / Git Bash 
git commit -m "docs(inception): analisis y reflexiones sobre scopes por Tu Nombre"

Presentamos a tu Mejor Amigo: El Árbol Gráfico de Git

Muchos estudiantes se sienten perdidos porque no "ven" las ramas. Memoriza este comando, porque te acompañará el resto de tu carrera como desarrollador:

Comando Maestro de Inspección 
git log --graph --all --oneline

¿Qué hace cada una de estas opciones mágicas?

  • --graph: Dibuja con líneas y asteriscos las bifurcaciones y uniones de las ramas en texto ASCII.
  • --all: Te muestra TODAS las ramas del repositorio (tanto las locales tuyas como las remotas de GitHub), no solo en la que estás colocado.
  • --oneline: Condensa cada commit a una sola línea limpia (hash corto + mensaje).
Ejemplo visual de lo que verás en tu consola
* 7f2a1b9 (HEAD -> feature/inception-tu-nombre) docs(inception): analisis y reflexiones sobre scopes por Tu Nombre
|
* daff28d (origin/main, origin/HEAD, main) generar laboratorio con docker y clase inicial
* ba7e45d git reset and git partial deployments
* 34a44ba practica deployhs git

¡Observa la magia! Tu rama (HEAD -> feature/...) está un commit por delante de main. Acabas de ver en vivo la divergencia de tu universo paralelo.

Subir la Rama, Committers y el Pull Request

Cómo colaborar en GitHub bajo una rama main protegida profesionalmente.

1. ¿Qué es un Committer / Colaborador?

Cualquier persona en Internet puede ver un repositorio público, pero solo los committers autorizados tienen permiso para subir código.

Requisito Previo Imprescindible: Facilitar tu usuario de GitHub

Para que el comando git push funcione y no te devuelva un error de "Permission to ... denied to user", debes haberle pasado tu nombre de usuario de GitHub al profesor para que te envíe una invitación de colaborador al repositorio oficial. Revisa tu correo o las notificaciones de GitHub para aceptar la invitación antes de subir tu rama.

2. ¿Por qué el profesor ha protegido la rama main?

En proyectos profesionales reales (en Google, Microsoft, bancos, startups), nadie puede hacer git push origin main directamente.

El profesor ha activado las Reglas de Protección de Ramas (*Branch Protection Rules*) en GitHub:

  • Se bloquea el push directo sobre main para evitar que un despiste borre el trabajo común.
  • Se exige obligatoriamente un Pull Request (PR) y la aprobación de un revisor humano (el profesor).
  • Esto garantiza la calidad del código, fomenta la revisión por pares (*Code Review*) y previene desastres.

3. Subir tu rama a GitHub

Sube tu rama local al servidor en la nube ejecutando:

Subir rama personal 
git push -u origin feature/inception-tu-nombre-apellido

* La opción -u (o --set-upstream) enlaza tu rama local con una rama idéntica en GitHub para que en el futuro solo tengas que escribir git push o git pull.

4. Abrir el Pull Request (PR) en GitHub

Un Pull Request es una solicitud formal donde le dices al dueño del proyecto: "Oye, he terminado mi mejora en mi rama personal; por favor, revísala y fúndela (*merge*) dentro de tu rama main".

Paso a paso en la web de GitHub:
  1. Entra en el repositorio: https://github.com/fjbanezares/ufv-bootcamp-2026.
  2. Verás un aviso amarillo arriba con tu rama y un botón verde que dice "Compare & pull request". Haz clic en él. (Si no aparece, ve a la pestaña Pull requests y pulsa "New pull request").
  3. Verifica que las flechas apunten en la dirección correcta:
    base: main  ←  compare: feature/inception-tu-nombre-apellido
  4. Escribe un título profesional:
    feat(inception): análisis de scopes y reflexiones por Tu Nombre
  5. En la caja de descripción redacta un breve resumen explicando qué has comentado y qué has aprendido.
  6. Haz clic en el botón verde "Create pull request".

En cuanto lo crees, el profesor recibirá una notificación, inspeccionará tus cambios en la pestaña Files changed y hará clic en Merge pull request para incorporar tu análisis a la rama maestra de la clase.
